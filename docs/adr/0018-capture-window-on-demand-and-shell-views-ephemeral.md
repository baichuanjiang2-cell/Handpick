# 截屏窗口默认按需创建，控制中心栏目子视图离场即销毁

Status: accepted

本轮性能改造（待机内存 -50% 目标）里两处窗口生命周期决策：

**截屏覆盖层（capture.html）不再常驻**。`保留截屏窗口` 默认值从 `true` 翻转为 `false`：启动不再创建隐藏的截屏渲染进程（挂着 753KB fabric 系 bundle + native 模块），首次截屏时按需创建，截完销毁。设置项保留，想要「秒开截屏」的用户可以开回；构建产物经 minify 后 bundle 缩到 506KB，按需加载的延迟被压到几百毫秒。`keepClip=true` 时的「关闭即隐藏 + 整页 reload」老路径原样保留给选择常驻的人。

**控制中心的栏目子视图（翻译 / AI 识图 / 设置）不再常驻**。原来首次切进栏目后 `WebContentsView` 一直活着；改为：切到其他栏目时销毁旧视图，窗口最小化收进任务栏时销毁全部视图，还原时由渲染端 `visibilitychange` 重发 `shellSection` 按需重建。待机内存只剩壳本身 + 默认的剪贴板历史页。

## Considered Options

- **保留常驻截窗 + backgroundThrottling** — 放弃：节流只压 CPU 不压工作集，常驻渲染进程的几十 MB 在待机时一分不少。
- **栏目子视图只隐藏不销毁** — 放弃：隐藏视图的渲染进程照样吃内存，与本轮目标直接冲突。
- **销毁时机只选「切栏目」不含「最小化」** — 放弃：用户停在翻译页收起壳是常态，待机内存要的就是这个场景下的降幅；代价是还原时短暂重建延迟与页内临时状态（翻译输入框、AI 识图当前图）丢失，属本轮共识里已接受的「性能特征变化」。
- **主页面也常驻省启动开销** — 放弃：[ADR 0004](./0004-clipboard-history-standalone-window.md) 已定按需打开，实测正确，不动。

## Consequences

- `保留截屏窗口` 的读取从模块顶层移到 `whenReady`（`setDefaultData` 之后）：原来模块顶层读时默认值还没注入，读到的是 `undefined`，**配置里没有显式写这个键的安装（含全新安装与本分支维护者本人）从未真正常驻过截窗**——旧代码的「默认 true」只是纸面默认。翻转默认值 + 修正读取时序后，文档化的行为与实际行为终于一致；配置里显式存过 `true` 的安装不受影响。
- 控制中心在别的栏目停留时收壳再打开，会回到该栏目但页内未保存的临时输入不复原；**翻译历史**、设置等持久数据不受影响。
- 截窗按需路径（`getClipWin` 懒创建）从「少数人的设置」变成正式路径，回归测试要覆盖它。

## 待机工作集裁剪（同一目标的补充手段）

实测发现：待机内存的大头不在可增删的功能，而是 Electron 的固定进程开销（main ≈91MB、GPU ≈62MB、网络服务 ≈46MB、crashpad ≈35MB、控制中心渲染 ≈104MB）。窗口层面的手段榨干后，补上**工作集裁剪**（`src/main/memoryTrim.ts`）：没有任何可见窗口且无贴图时，对主进程与全部 Chromium 子进程调 `SetProcessWorkingSetSize(-1,-1)`——Chrome 最小化时的同款做法。物理页移交系统待备列表，恢复窗口按需软调页回（毫秒级），系统内存紧张时待备页可立即回收。触发点：控制中心最小化、主窗口关闭、截屏隐藏/关闭、贴图关闭，以及启动 90 秒后的首次待机检查（开机即最小化、无人碰窗口的场景没有事件可触发）；启动后 60 秒内不裁（避免页面还在加载就调页回）。非 Windows 或 FFI 加载失败时静默跳过。

实现要点（踩过的坑，留档）：`SetProcessWorkingSetSize` 必须取 **kernel32 的原名导出**（psapi.dll 那个是转发导出，koffi 不解析转发）；句柄用 **intptr 整数**传递，当前进程走 `-1` 伪句柄；子进程 `OpenProcess` 的权限位要含 **PROCESS_SET_QUOTA(0x0100)**——记成 0x0400 会拿到 ERROR_ACCESS_DENIED。

同口径实测（独立 userData，10 分钟窗口）：待机工作集中位数 **375.3MB → 130.1MB（-65.3%）**，待机 CPU **1.7 → 0 CPU 秒/小时**。
