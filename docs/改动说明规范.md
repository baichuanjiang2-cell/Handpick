# 改动说明规范

**每次改动收尾时，怎么跟用户说「做了什么」和「有什么影响」。**

## 为什么有这份文件

用户自述**完全不懂技术**。这份说明的目的不是留档（留档是 commit message 和 Release notes 的事），而是让他在**不读代码**的前提下判断三件事：

1. 这次改的东西，他能感知到吗？
2. 会不会动到他的数据或设置？
3. 他要不要做点什么（重启 / 重新打包 / 改设置）？

## 什么时候写

- **只在任务收尾写一次**。中途不发文字进度 —— 工具调用在界面上本来就可见，打包、跑验证这类长任务也不例外。
- 一次说明对应**一个任务**（一条用户消息驱动的一轮工作），不是一次 commit、也不是一个文件。
- **纯内部改动一句带过**，例如「这轮只做了内部整理，行为没变」。判定见「什么算纯内部改动」。
- 没做成的任务**照写**，见「失败时」。

## 格式

```
<结论行>

### 专业版
<≤15 行>

### 通俗版
<≤5 行>
```

- **结论行**：`✅ 做完了` / `⚠️ 做了一半` / `❌ 没做成，卡在…`，后面跟一句「这次到底发生了什么」。
- 两段标题**固定**，专业版在前、通俗版在后。
- **「行」按 markdown 的列表项 / 段落算**（一个换行算一行），不是按字数 —— 中文一句话 40 字就该断行了。
- 文件路径一律用行内代码，方便复制。

## 专业版

读者是「想先扫一眼硬信息」的用户。所以**结构固定、术语必解释**：每个机制类词第一次出现时，后面跟一句括号人话。

小项按顺序，**后四项没有就省，不硬凑**：

| 小项 | 内容 |
|---|---|
| 改了什么 | 哪个文件、哪一处、改成什么 |
| 为什么 | 不这么改会出什么问题 |
| **你需要做什么** | **要重启 / 要重新打包 / 要改设置 / 不用管** —— 加粗，放显眼位置 |
| 数据影响 | 数据目录、配置、剪贴板历史会不会动 |
| 风险与回退 | 出问题怎么退回去 |
| 我没验证到的 | 只测了什么、没测什么 |
| 验证方式 | 跑了哪些命令、实测到什么数字 |
| 提交 | commit hash / PR 号（有则写） |

**「影响」的覆盖要求**：

- **必写**：① 他能看到的行为变化 ② 数据 / 配置会不会动 ⑥ 要他做什么
- **有则写**：④ 风险与怎么回退 ⑤ 我没验证到的部分
- **只在有实测数字时才写**：③ 性能与资源开销 —— 没数字就是编，宁可不说

**⑤ 是最重要的一项**：把「我猜的」和「我验过的」分开说。这是用户最容易被误导的地方。

## 通俗版

读者是**用户本人**（不是转述稿，不需要为外人补背景），但按**完全不懂技术**来写。

- 3~5 行。
- 可以有文件名和路径（否则他没法定位到具体东西），但**机制类词**（进程、渲染、合成器、DPI、哈希、指纹……）第一次出现必须紧跟一句人话。
- **不用类比硬凑**：有些事没有通俗说法，类比过度就是误导，比说实话更糟。宁可写「这块你不需要知道细节」。
- 结尾要落到「**你要做什么**」上，哪怕是「不用管」。

## 什么算纯内部改动

**默认写两份。** 只有能明确归入下面白名单的，才一句带过：

- 只改格式、缩进、lint
- 只改注释
- 内部改名（对外行为不变）
- 只改测试
- 只改**内部记录类**文档（ADR、工作记忆）

两条边界：

- **「文档」要拆开看**：改 `docs/新手使用指南.md` 这类**给用户看的**文档，算「能感知」，要写两份；改 ADR 这种内部记录，才一句带过。
- **有疑问就写两份**（保守优先）。口子开大了，会用「这是内部改动」把该让他知道的改动一笔带过。

## 失败时

先给结论行（`⚠️` / `❌`），再照常写两份，而且 **⑤「我没验证到的部分」必须写、不许省**。

失败时的说明比成功时更重要 —— 成功时用户只需要确认，失败时他要判断要不要换方向。

## 平时回答的默认写法

改动说明只是其中一种场合。平时回答技术问题也按这几条：

- 先给结论，再给理由。
- 术语第一次出现时配一句人话。
- 不确定的地方明说「这是推测」，不要和实测结果混在一段里。
- 结论取决于某个他需要做的选择时，把选项和推荐一起给，别只抛问题。

## 和别的文档的分工

| 文档 | 写给谁 | 内容 |
|---|---|---|
| 本文件 | 助手自己 | 每次改动怎么汇报 |
| `docs/新手使用指南.md` | 用户 | 这个应用怎么用 |
| commit message | 未来的技术读者 | 为什么这么改 |
| Release notes | 下载的人 | 这个版本新增 / 修了什么 |

**不另开变更日志**（如 `docs/变更记录.md`）：手写日志腐烂快，而且会和 commit message、Release notes 三份说法打架，比没有更糟。

## 生效机制

- 本文件是正文，但 `docs/` 有几十个文件、平时不会全读 —— 所以 `AGENTS.md` 里有一节摘要 + 指向本文件的指针，那才是每次会话都会被读到的入口。
- 用户级记忆（跨项目）里另有一条同样的规则，让它在别的项目也生效。
- ⚠️ `AGENTS.md` 是上游文件。这条规范属于本分支的定制，**`feature/clipboard-history-upstream` 精简分支要剔除它**。
